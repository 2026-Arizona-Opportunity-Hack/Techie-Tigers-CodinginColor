# Backend fixes — Nov 14

Five changes. The first three were crashes; the last two change who can add donors and what happens when they do.

**Action needed:** run `backend/database/migrations/2026-11-14_fundraising_can_add_donors.sql` once in the Supabase SQL editor. Until you do, fix 4 won't work on the live database (fundraising adds will be refused).

---

## Fixes 1–3: `service_client` used without calling it

`service_client` in `app/db.py` is a **function** that returns the Supabase client. Three places used it as if it were the client itself:

```python
service_client.table("donors")      # wrong: AttributeError, request returns 500
service_client().table("donors")    # right
```

Python doesn't catch this until the line actually runs, which is why the server started fine.

| # | Where | What was broken |
|---|-------|-----------------|
| 1 | `routers/donors.py` — `POST /donors` | Admin/fundraising couldn't add a donor at all. |
| 2 | `routers/communications.py` — `POST /communications/{id}/mark-sent` | For thank-yous, the message was saved as sent, then the request crashed before setting `last_thanked_at`. The user saw an error even though it was logged. |
| 3 | `routers/next_steps.py` — `POST /jobs/quarterly-drafts` | It imported `service_client as sdb` and called `sdb.table(...)`, so the whole job crashed. Now `sdb = service_client()` at the top of the function. |

## Fix 4: Fundraising can add donors, enforced by the database

**Before:** the database only let admins insert donors, and `POST /donors` worked around that by using the service client (which skips all security rules) for fundraising. The real permission lived only in Python, which goes against the rule in `decisions.md` that security is enforced by Postgres.

**Now:** every role inserts as themselves (`user.db`), and the database decides:

| Role | Can add? | Who owns the new donor |
|------|----------|------------------------|
| Board member | Yes | Themselves (unchanged) |
| Admin (CEO) | Yes | Whoever they pick, or round-robin |
| Fundraising | Yes (new) | Always round-robin. They can't pick, because only the CEO assigns owners. |

Two database changes (in `database.sql` and the migration):

- Policy `donors_admin_insert` (admins only) was replaced by `donors_staff_insert` (`is_staff()` = admin or fundraising).
- The round-robin trigger now clears any owner a fundraising user sends before it picks one. That way the rule holds even if someone calls Supabase directly instead of going through our API.

## Fix 5: Hand-added donors get the same duplicate check as imports

**Before:** imports fuzzy-matched every new donor against everyone else, but a manual add only checked for an exact email. A board member adding "Bob Smith" (no email) while "Robert Smith" already existed would quietly create a duplicate.

**Now:** after a donor is added, `POST /donors` runs the same matcher and puts any hits in `duplicate_candidates` for the CEO to review. Nothing is merged automatically.

- The matching rules haven't changed: name similarity ≥ 90, or ≥ 60 plus the same phone. Inactive and merged donors are ignored. Exact-email pairs are skipped, since the unique email index already blocks those.
- The queue entry's reason ends in "(added by hand)" so the CEO can tell it apart from import matches.
- The response gains one field, `"possible_duplicates": <count>`. It returns only a count because a board member isn't allowed to see other members' donors, so we don't say who matched. The frontend can show something like "This may be a duplicate, so the CEO will review it."
- The check runs with the service client because it has to compare against all donors, not just the ones the user can see. Nothing from those other donors is sent back to the user.

**Code:** the per-donor matching loop in `importers/dedupe.py` moved into a shared helper (`_matches`). Imports and the new `find_duplicates_for()` both use it, so the two can't drift apart. Import behaviour is unchanged.

## How it was checked

- `python -c "import app.main"` loads every router.
- The matcher, against sample donors: "Bob Smith" + same phone → matches "Robert Smith"; "Jane Doe" with no email → matches the existing Jane Doe; same email → no review entry; unrelated name → nothing; inactive donors → never matched. An import plan run through the refactored code gives the same candidates as before.
- **Not yet tested against the live Supabase database:** the new policy and trigger, and a real fundraising-user add. Try that after running the migration.
